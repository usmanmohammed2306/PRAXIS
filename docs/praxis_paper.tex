\begin{abstract}
Small open-weight tool-calling agents typically fail not because they
lack capability, but because they lack a confident, reusable
\emph{procedure} for the task at hand. We present
\textbf{PRAXIS} (Procedural Retrieval-Augmented eXperience-Informed
System), a controller that wraps any frozen large language model
(LLM) with a continually growing, leakage-safe procedural memory.
PRAXIS distills successful and recoverable trajectories from any
controller into compact \emph{Process Memory Cards}, retrieves the
top-$k$ relevant cards at every decision step via a hybrid
BM25$+$TF-IDF retriever with domain and quality boosts, and renders
them into a bounded \emph{Tactical Playbook} injected into the
system prompt. Every \emph{mutating} tool call is additionally guarded
by a SABER-style reflection pass that asks the same model whether
the observed evidence confirms the action. We benchmark PRAXIS
against three controller baselines---vanilla tool-calling, Act-only,
and ReAct---on $\tau$-bench retail, $\tau$-bench airline, and
BFCL~V4, with all four controllers sharing the same frozen base
model, temperature, tool schemas, and step budget. A three-layer
train/test fairness protocol (run-level promotion gate, per-record
split tag, and pre-warm separation) ensures that PRAXIS's memory is
populated exclusively from training-pool trajectories and never from
the tasks on which it is scored. The contribution is methodological:
zero fine-tuning, no in-context examples, no benchmark-answer
retrieval, and a strict procedural---rather than parametric---path
to continual improvement for tool-using agents.
\end{abstract}

\section{Introduction}

Tool-calling agents built on small open-weight LLMs (7B--32B
parameter range) routinely under-perform on multi-step benchmarks
such as $\tau$-bench~\cite{taubench} and the Berkeley Function
Calling Leaderboard (BFCL)~\cite{bfcl}. The dominant failure mode
is not arithmetic or syntactic: it is \emph{procedural}. The model
selects a plausible first tool, observes a result, and then
oscillates --- repeating searches, missing a confirmation step,
acting before evidence is gathered, or violating a policy
constraint it has not internalized. Fine-tuning closes the gap but
is expensive, slow to iterate, and risks catastrophic forgetting on
unrelated capabilities. Static in-context examples plateau
quickly and leak benchmark structure into the prompt.

We argue that what these agents lack is a \emph{continually
growing procedural memory}: a compact, retrievable record of
``how a task like this is done,'' learned from prior interactions
and injected as conditioning at decision time. We instantiate this
idea as \textbf{PRAXIS}, and contribute:

\begin{itemize}
  \item A four-stage \emph{Memory Loop} (Section~\ref{sec:method})
    --- Distillation $\to$ Storage $\to$ Retrieval $\to$ Mutation
    Guard --- that turns any controller's trajectories into reusable
    process cards.
  \item A bounded \emph{Tactical Playbook} ($\le 2{,}400$ characters)
    rendered from the top-$5$ retrieved cards, refreshed every two
    steps, so context cost is constant in the bank size.
  \item A research-paper-grade train/test split protocol that
    extends to benchmarks lacking an upstream split, enforced at
    three independent layers, so PRAXIS is never evaluated on the
    trajectories it learned from (Section~\ref{sec:fairness}).
  \item An open prototype with exactly two shell entry points,
    designed to run end-to-end on a single 1$\times$A100 GPU for
    all four controllers in a budget-bounded ($\sim$10--15~h) full
    evaluation.
\end{itemize}

PRAXIS is a \emph{methodological} contribution. The base model is
frozen across every condition; only the controller varies; and the
memory bank itself is, by construction, the only artifact that
changes between runs.

\section{Related Work}

\textbf{ReAct and reasoning-action interleaving.}
ReAct~\cite{react} demonstrated that interleaving short
\texttt{Thought:} prefixes with tool calls improves multi-step tool
use on Q\&A and WebShop. We treat ReAct as one of our three
controller baselines, alongside an \emph{Act-only} variant (no
reasoning prose) and \emph{vanilla tool-calling} (native function
calling with a minimal policy prompt).

\textbf{Retrieval-augmented generation (RAG).}
Classical RAG~\cite{rag} retrieves documents to ground an answer.
PRAXIS retrieves \emph{procedures} --- compact, distilled
descriptions of tool sequencing, recovery, and policy --- and
injects them as conditioning for the controller, not as candidate
answers.

\textbf{Reflexion and self-critique.}
Reflexion~\cite{reflexion} stores natural-language reflections
between episodes. PRAXIS's distillation step performs an explicit
PII-stripping and schema-bound projection (Section~\ref{sec:distill}),
and our \emph{SABER mutation guard} (Section~\ref{sec:saber})
intervenes \emph{within} an episode and only on write tools.

\textbf{Tool benchmarks.}
$\tau$-bench~\cite{taubench} provides realistic retail and airline
domains with a simulated user. BFCL~\cite{bfcl} provides
single- and multi-turn function-calling tasks with schema-grounded
ground truth. We use both to test whether a single, frozen base
model improves \emph{on the same controller code path} when given
procedural memory rather than not.

\section{Method}\label{sec:method}

PRAXIS is composed of four components (Fig.~\ref{fig:loop}):
\textbf{(i)} a \emph{Distiller} that converts a raw trajectory into
a Process Memory Card; \textbf{(ii)} a \emph{Memory Store} of seed
and runtime cards per domain; \textbf{(iii)} a \emph{Hybrid
Retriever} with a Tactical Playbook renderer; and \textbf{(iv)} a
SABER \emph{mutation guard} for write tools.

\subsection{Process Memory Cards}

A Process Memory Card is a small JSON object emitted by the
Distiller. It captures the \emph{intent} of a task, the
\emph{minimum tool sequence} that completes it, the
\emph{evidence required} before mutating tools, a
\emph{confirmation point}, and one \emph{common trap} or
anti-pattern. It does \emph{not} store messages, observations,
gold actions, IDs, emails, payment methods, dates, or argument
values --- a defence-in-depth check in the storage layer rejects
any card that retains raw trajectory fields.

\subsection{Distillation}\label{sec:distill}

Given a trajectory record $r = (\text{task\_id}, \text{messages},
\text{reward}, \text{info})$, the Distiller (i)~strips PII tokens
and forbidden literal strings; (ii)~derives a domain label from
\texttt{info.environment}; (iii)~extracts the ordered tool-name
sequence (collapsing retries) and a confidence score from
$(\text{reward}, \text{steps}, \text{recovered})$; and (iv)~assigns
a quality score used downstream by the retriever. Records flagged
as held-out test split (Section~\ref{sec:fairness}) are dropped
before distillation.

\subsection{Hybrid Retrieval}

Let $\mathcal{C}_d$ be the merged seed and runtime card corpus for
domain $d$. At step $t$ the controller forms a query
$q_t$ from (a)~the user's last utterance, (b)~the tool names invoked
so far, and (c)~the current working-state summary. Retrieval scores
each card $c$ as
\begin{equation}
s(c, q_t) = 0.60 \cdot \mathrm{BM25}(c, q_t) + 0.40 \cdot \mathrm{TFIDF}(c, q_t)
\end{equation}
\begin{equation}
+\; 0.05\,\mathbb{1}[\mathrm{dom}(c)=d] + 0.05 \cdot \mathrm{quality}(c)\,.
\end{equation}
A diversity cap of three cards per card-category prevents the
top-$k$ slate from collapsing onto one procedure family. The
top-$k=5$ cards are then deterministically rendered into a
\emph{Tactical Playbook} of at most $2{,}400$ characters and
injected into the system prompt. The playbook is recomputed every
two steps so it tracks the current sub-task without paying the
retrieval cost every turn.

\subsection{SABER Mutation Reflection}\label{sec:saber}

Many controller failures we observed in pilot runs are
\emph{premature mutations}: cancelling, modifying, or submitting
before the user's intent and evidence are confirmed. SABER guards
every \emph{write} tool with a single same-model reflection call of
the form ``Given the observations so far, does the evidence confirm
that this action is safe \emph{and} requested?'' --- returning
\textsc{allow} or \textsc{block}. Read tools execute immediately.
The reflection is bounded to one extra LLM call per write and is
not used to plan, only to gate.

\section{Train/Test Fairness Protocol}\label{sec:fairness}

Because PRAXIS's bank grows from trajectories, any sloppy boundary
between ``trajectories that build the bank'' and ``tasks that score
the agent'' would invalidate the comparison. We enforce the
boundary at three independent layers:

\begin{enumerate}
  \item \textbf{Run-level gate.} The runner's
    \texttt{\_should\_promote()} returns \texttt{False} for runs
    whose \texttt{task\_split} is \texttt{"test"}, so no
    distillation is invoked on a pure test pass.
  \item \textbf{Record-level gate.} Every record is stamped with
    \texttt{info.task\_split}; the pipeline's
    \texttt{\_is\_test\_split\_record()} drops any
    \texttt{"test"}-labeled record before distillation, regardless
    of how the runner is invoked.
  \item \textbf{Pre-warm separation.} An explicit pre-warm phase
    runs PRAXIS only on the train slice; the subsequent four-way
    evaluation runs only on the test slice.
\end{enumerate}

For benchmarks that ship no upstream split, we construct one
deterministically (Table~\ref{tab:splits}).

\section{Experimental Setup}

\subsection{Base Model and Controllers}

All four controllers share one frozen base LLM served via an
OpenAI-compatible local endpoint. The four conditions are:

\begin{itemize}
  \item \textbf{baseline} --- vanilla native tool-calling with a
    minimal policy prompt.
  \item \textbf{act} --- Act-only ablation: tool calls without any
    reasoning prose.
  \item \textbf{react} --- ReAct~\cite{react}: a single short
    \texttt{Thought:} before each tool call.
  \item \textbf{praxis} --- PRAXIS controller as described in
    Section~\ref{sec:method}.
\end{itemize}

Temperature, maximum steps per task, tool schemas, and the
litellm-truncation patch are identical across conditions.

\subsection{Benchmarks and Metrics}

We evaluate on three benchmarks:

\begin{itemize}
  \item \textbf{$\tau$-bench retail}~\cite{taubench} --- 115 test
    tasks averaging 5.1 expected actions.
  \item \textbf{$\tau$-bench airline}~\cite{taubench} --- internal
    test slice (Section~\ref{sec:fairness}); upstream provides no
    train split.
  \item \textbf{BFCL V4}~\cite{bfcl} --- categories
    \texttt{simple}, \texttt{multiple}, \texttt{parallel},
    \texttt{parallel\_multiple}, \texttt{multi\_turn\_base};
    internal per-category test slice.
\end{itemize}

For $\tau$-bench we report task success rate (binary reward $\in
\{0,1\}$), mean reward, and average number of LLM calls per
trajectory. For BFCL we report tool-name coverage (intersection
over expected) and binary success at coverage $\ge 1.0$. All runs
report per-card retrieval statistics (cards loaded, cards used,
mean playbook length, refresh count) for the PRAXIS condition.

\subsection{Compute}

The entire matrix --- four controllers $\times$ three benchmarks,
plus pre-warm passes and summary aggregation --- is designed to run
on a single 1$\times$A100 within a $\sim$10--15~h wall-clock budget
at the medium profile ($30$ tasks $\times$ $3$ trials for
$\tau$-bench cells, $40$ tasks for BFCL).

\subsection{Diagnostics reported for the PRAXIS condition}

In addition to task metrics, every PRAXIS run logs:
trajectories with retrieval stats; reflection calls and reflection
blocks; mutating tool-call counts; mean cards loaded and cards
used; mean playbook character length; retrieval backend mix; and
total retrieval refresh count. These diagnostics let us
distinguish \emph{retrieval impact} from \emph{reflection impact}
post-hoc, without further runs.

\section{Discussion}

\textbf{Why no fine-tuning.}
Fine-tuning a small open model on benchmark trajectories collapses
two confounders --- procedural knowledge and parametric drift ---
into one. PRAXIS keeps the base model bit-identical across all four
controllers, isolating the controller axis. Any improvement we
observe is attributable to procedural memory and the SABER guard,
not to weights.

\textbf{Why bounded playbook length.}
A naive ``inject everything relevant'' policy explodes context cost
as the bank grows. The $2{,}400$-character playbook ceiling makes
prefill cost a function of $k$, not of $|\mathcal{C}_d|$.

\textbf{Limitations.}
(i)~PRAXIS depends on at least one successful or
recoverable-failure trajectory in the train pool per task family;
on a fully cold start it reduces to vanilla tool-calling plus the
SABER guard. (ii)~Distillation is heuristic; a learned distiller
would likely yield denser cards but adds a moving part we
deliberately avoid in this prototype. (iii)~The BFCL test slice is
defined deterministically per category but the original benchmark
does not endorse a canonical split; we recommend reporting both
$f=0.25$ and $f=0.50$ when extending this work.

\textbf{Reproducibility.}
The repository ships exactly two shell scripts
(\texttt{setup\_env.sh}, \texttt{run\_project.sh}) and one
configuration file (\texttt{configs/project.yaml}). Every run
writes a \texttt{run\_summary.json} containing the resolved
configuration, the train/test thresholds, the promotion manifest,
and the aggregated retrieval logs.

\section{Conclusion}

PRAXIS shows that a frozen small LLM can improve on multi-step
tool-calling benchmarks via \emph{procedural} memory --- distilled,
bounded, retrieved, and reflection-guarded --- without any
gradient updates and without leaking the evaluation set. Our
three-layer train/test fairness protocol generalizes to benchmarks
that ship no upstream split, and our reporting template fixes the
metric set in advance so results cannot be cherry-picked
post-hoc. Future work includes (i)~learned distillation,
(ii)~cross-domain card transfer, (iii)~larger base models held
constant across the comparison, and (iv)~adversarial perturbations
of the training-pool trajectories to test bank robustness.
